# 《谁最圆》好友排行榜设计文档

- 日期：2026-11-01
- 状态：待评审
- 范围：**仅历史好友排行榜**。好友对战本期不做（架构预留，不写代码）。

---

## 一、目标

给《谁最圆》加一个好友排行榜：玩家能看到「也玩这个游戏的好友」里谁的历史最高分最高。

榜上分数必须**可信**——不能靠改内存刷分。

## 二、已确认的决策

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| D1 | 榜的口径 | **历史榜（总榜）** | 与现有「最高分」存档一致；不需要周切换与跨周过滤 |
| D2 | 世界榜 | **不做**，但云端双写 `scores` 集合攒数据 | 将来上世界榜时客户端与云函数都不用改 |
| D3 | 整体方案 | **开放数据域 + 云端权威分** | 好友榜只能走开放数据域；分数可信要靠云端重算 |
| D4 | 上传触发 | **只在破纪录时上传**（`S > H`） | 这一局无论真假都上不了榜的，云端没必要知道 |
| D5 | 上传分级 | **S ≥ 95 同步等待云端结论；S < 95 异步不阻塞** | 复用现有 `GUARD_CFG.HIGH_SCORE = 95`；高分才有防作弊价值 |
| D6 | 榜上分 vs 本地分 | **榜上 = 云端权威分；本地 = 乐观值** | 本地立刻给反馈，榜上永不虚高 |
| D7 | 评分引擎共享 | **抽出 `shared/scoring.js`，主域与云函数共用** | 结构性保证两端算法一致，不依赖人记得同步 |
| D8 | 主域改造幅度 | **最小侵入**，不拆 `js/` 目录 | 1785 行单文件现在能跑、回归套件在，不为洁癖冒险 |
| D9 | 榜面视觉归属 | **样式参数由主域 `postMessage` 下发，开放域只管画** | 样式单一来源，既统一又不用跨 canvas 拼接 |

### 明确不做的事

- 好友对战（挑战发起、结果送达、订阅消息）
- 世界榜查询接口与榜单 UI
- 微信搜索 / 小游戏中心榜单曝光（后台配置可后补，数据格式已预留兼容）
- 段位图标在榜面上的绘制（第一版用段位名文字）
- 分组排行、赛季、赛季奖励

## 三、微信平台硬约束（设计的地基）

这些是**平台规定**，不是选择，直接决定了上面的方案。

| 约束 | 后果 |
|---|---|
| 主域**读不到**好友关系链数据 | 好友榜只能在开放数据域渲染 |
| 开放数据域数据**禁止传第三方服务器** | 不能「主域拉好友榜→传云端→云端算→回传」。榜单必须现拉现画 |
| 开放数据域**不能联网**、不能调云开发 | 云函数调用只能在主域 |
| 开放数据域**不能 `require` 主域代码** | 评分引擎不用进开放域（它只负责拉+排+画），但主域与云函数要共用它 |
| 开放数据域 → 主域**只能单向**（`postMessage` 主域→子域） | 开放域不能回调主域，主域得在固定时机下指令 |
| 主域 → 子域 `postMessage` 上限 1MB | 样式参数体积可忽略，数据不能塞进消息 |
| 共享画布 `sharedCanvas` 在页面切换 / `onShow` 后内容会丢 | 主域要能随时重新合成，开放域要能随时重画 |
| 开放数据域**不能加载主域图片资源** | 好友头像得自己 `wx.createImage()` 拉 URL + 失败兜底 |
| 托管数据只认**已上报过的用户** | 没完成过一次上报的好友不在榜上 |
| 托管数据读取受 `scope.WxFriendInteraction` 门禁 | 未开「向朋友公开」静默读不到 |
| `wxgame.score` 必须是 **Int32** | 分数一位小数 → 上报 ×10，显示 ÷10 |
| 后台排行榜 key **≤8 字符且全英文** | 用 `circle` |

## 四、总体架构

```
┌──────────────── 主域（game.js）─────────────────────────┐
│                                                        │
│  ① 本地评分 evaluate() ──→ 分数 S                       │
│       │                                                │
│       ├─ S ≤ H ──→ 直接结算（不上传）                    │
│       └─ S > H ──→ ② 上传笔迹到云函数                     │
│                        │                               │
│  ② wx.cloud.callFunction('score', {pts, sig, ...})       │
│                        │                               │
│  ③ 云端权威分 C ←── 云函数重算 + 校验                     │
│       │                                                │
│       ├─ C 通过 ──→ wx.setUserCloudStorage 上报 C        │
│       │              （主域直接调，不需要开放域参与）      │
│       ├─ 本地 H ← C（乐观更新）                          │
│       └─ 被判无效 ──→ H 不变，不上报                     │
│                                                        │
│  ④ 打开榜单面板                                         │
│       │ postMessage({type:'showLeaderboard', style:{...}})│
│       ↓                                                  │
│  ⑤ 每帧 ctx.drawImage(sharedCanvas, ...) 合成进主画布      │
└────────────────────────┬───────────────────────────────┘
                         │ 单向消息
┌────────────────────────↓───────────────────────────────┐
│              开放数据域（open-data/index.js）             │
│                                                        │
│  wx.getFriendCloudStorage({keyList:['circle']})          │
│  wx.getUserCloudStorage({keyList:['circle']})  ← 自己    │
│  wx.getUserInfo() → 头像 / 昵称                          │
│       ↓                                                │
│  归一化 → 排序 → 去重「我」→ 画到 sharedCanvas           │
│  （样式全部来自主域下发的 style 参数）                     │
└────────────────────────────────────────────────────────┘
                         │
                         ↓
              ☁️ 云函数 score（+ 云数据库）
```

### 为什么云端要重算而不上报分数

客户端自报分可以直接改成 100。云端拿笔迹重跑一遍 `evaluate()`，分数是**算出来的**，改内存无效。

这不是"更强的信任"，是**不同的信任模型**：自报分是声明，重算是证据。

## 六、数据契约

### 6.1 云函数 `score`

**入参**

```js
{
  pts: [ /* encodePts 输出：每点 [dx, dy, dt] 增量 */ ],
  clientScore: 92.4,       // 客户端自评分（仅作交叉校验参考，不作数）
  clientBest: 87.2,
  sig: [0.0123, -0.0456, ...],   // shapeSig 输出：64 个数字的数组（非字符串）
  guard: { hard: [], risk: 3, hits: ['clock_drift'] }   // 客户端 guardCheck 结果（辅助信号）
}
```

> ⚠️ **`sig` 是数组，不是字符串。** `shapeSig` 返回 64 个归一化径向残差（各保留 4 位小数）。云端跨玩家查重沿用 `isReplay` 的**平均绝对偏差**算法——`Σ|sig[i] − other[i]| / 64 < REPLAY_TOL` 判为重放——**不是字符串哈希**。`fnv` 只用于最高分存档自校验，与重放检测无关。

**出参**

```js
{
  ok: true,
  // 复用现有 judge() 的**四档**语义（不是三档）：
  //   ok         正常
  //   shadow     行为异常，成绩不计入最佳
  //   unverified 存在可疑特征但未达 shadow 门槛 —— 分数给，但标记为"未完全验证"
  //   reject     拒绝
  // （P2 实作时发现 judge() 实际有第四档 unverified，本文档原先漏写，已更正）
  verdict: 'ok' | 'shadow' | 'unverified' | 'reject',
  score: 92.4,          // 云端权威分
  level: 4,             // 段位索引
  newBest: true,        // 是否刷新该玩家的云端历史最佳
  best: 92.4,           // 云端认定的历史最佳
  reason: '',           // reject 时的说明文案
  cloudGuard: {         // 云端自己的防作弊判定
    risk: 0, hits: [], hard: [],
    note: '判定完全基于云端重算；clock_drift 未独立复核（上传协议不含回调时刻 h）'
  },
  clientGuard: {...},   // 客户端上报的 guard，原样回显供审计对比（**不参与判定**）
  scoreDelta: 0,        // 云端分 − 客户端分，交叉校验用
  replay: false
}
```

**客户端上报的 `guard` 不参与判定**，只回显供审计对比。
理由：客户端代码在攻击者手里，"客户端说自己有问题"的判断能被摘掉；
云端只能信自己重算出来的数据。

**云函数内部流程**

1. `cloud.getWXContext()` 取 `OPENID`（**不要信任客户端传的标识**）
2. 解码 `pts` → 点集；点数上限校验（> 900 直接 reject）
3. `evaluate(points)` → 分数与拟合结果
4. `guardCheck(raw, fit, score, sig)` → 风险分与 flags
5. `judge(...)` → verdict
6. **速率限制**：读 `scores` 中自己的 `lastSubmitAt` / `recentSubmits`，窗口内超阈值 → reject
7. **重放检测**：查 `submissions` 中 `sig` 是否已存在（异人使用）→ reject
8. 写 `scores`（仅当更高分）与 `submissions`（审计 + 重放检测）
9. 返回出参

### 6.2 云数据库集合

| 集合 | 文档结构 | 写入时机 |
|---|---|---|
| `scores` | `{_id: openid, score: Int, level: Int, updatedAt, lastSubmitAt, recentSubmits}` | **服务端权威「有效」最高分** + 防作弊状态。`score`/`level`/`updatedAt` 只在成绩**有效**（`ok`/`unverified`）且更高时更新；`lastSubmitAt`/`recentSubmits` **每次调用都更新**（速率限制的基准）。**本期只写不查**（世界榜数据源） |
| `submissions` | `{_id: auto, openid, sig, score, verdict, ts}` | 每次调用都写（含被拒的），用于重放检测与审计 |

`submissions` 增长控制：保留最近 7 天，用云函数定时触发器清理（本期可先不做，靠量级撑）。

### 6.3 托管数据格式（`wx.setUserCloudStorage`）

用**微信标准格式**（这样以后想上搜索/小游戏中心曝光不用改结构）：

```json
{
  "wxgame": {
    "score": 924,
    "update_time": 1780000000
  },
  "level": 4,
  "v": "ok"
}
```

- key：`circle`（≤8 字符全英文）
- `wxgame.score` = **云端权威最高分** × 10（Int32 要求）
  写最高分而不是本局分：`wxgame.score` 是小游戏中心/排行榜的标准字段，语义就是"最好成绩"；
  写本局分会让 `score`（按本局）与 `level`（按最高分）两个字段口径打架，
  榜面会出现"80 分 · 大师段位"这种自相矛盾
- `level` 放在 `wxgame` 同级（`wxgame` 下不可自定义字段，同级可以）= 最高分对应的段位
- `v` = verdict 标记（`ok` / `unverified`）
  §7.4 要求 unverified 的分要给但标出"未完全验证"；开放数据域读不到 `submissions`
  （不能发网络请求），所以那个角标只能靠托管数据自己带 verdict 字段
- `update_time`：Unix 秒

**主域 → 开放域**


```js
{ type: 'hideLeaderboard' }
```

**`rankNames` 为什么由主域发**：开放数据域**不能** `require` 主域的 `shared/scoring.js`
（平台限制：主域 ↔ 开放域不能互相 require），自己复制一份段位表必然漂移 ——
云函数那份已经有 sha256 断言了，主域这份不能再分叉。所以主域算好名字表发过去，
开放域用托管数据里的 `level` 索引取名。

**开放域 → 主域**：无（平台限制，单向）。主域靠固定时机驱动。

> ⚠️ **共享画布的位图必须等于主域画布的物理尺寸**（P4 真机验证时踩过）：
> 我在**开放域**里设 `canvas.width = 700 × scale` = 1126×1897，平台给的是 **402×874**
> —— 屏幕的**逻辑**尺寸（1206×2622 ÷ dpr 3）。而主域画布是 1206×2622 **物理**像素，
> 铺满屏幕时就是**放大 3 倍** → 文字发虚。
>
> 官方写法也是「把 sharedCanvas 铺满主画布」（`drawImage(sc, 0, 0, canvas.width, canvas.height)`），
> 所以位图得是物理像素大小。改法：
>
> 1. **主域**设置：`wx.getOpenDataContext().canvas.width = env.width`（主域知道物理尺寸）；
> 2. **开放域**读回**实际**画布尺寸，按它算密度：`密度 = 实际画布宽 / 设计宽`；
> 3. 主域 **1:1 贴整屏**（位图与主画布同尺寸时天然 1:1）。
>
> 平台若仍然钳制（回到 402×874），开放域会自动降级成小密度 —— **布局不变，只是不够锐**，
> 不会错位也不会裁切。
>
> ⚠️ **`scale` 不是设备像素比**（P4 真机验证时踩过）：
> 共享画布是**物理像素**的，主域又把它画进设计坐标矩形（ctx 上有 `view.scale` 的缩放）。
> 要让两边内容一样大，共享画布的密度必须等于**主域的 `view.scale`**（≈1.56），
> 而不是设备的 `pixelRatio`（≈3）。传错了 → 内容在共享画布里被放大 → 被裁切 →
> 主域再拉回来 → **真机上看到文字放大三倍、卡片右边被切掉**。
> 开放数据域那边还会**读回实际画布尺寸**，平台若裁剪了就按比例补偿（宁可略糊，不可错位）。

> ⚠️ **单向这条约束推翻了 §8.2 的一句**：§8.2 原本写「名次由开放域算好，主域只画文案」——
> 但名次算好了也**传不回主域**。所以「我的历史最高 X · 第 N 名」那一行
> **必须画在开放域的 sharedCanvas 里**（见 §8.2 修订）。

**样式参数防御**：开放域对 `style` 每项做范围钳制（缺失/越界 → 用默认值），避免主域传错导致整张榜歪掉。

## 七、关键机制

### 7.1 上传触发策略（D4 + D5）

```
本地算出 S，本地历史最高 H
  │
  ├─ S ≤ H ─────────────────────→ 不上传，直接结算
  │                                （这一局无论真假都上不了榜）
  │
  └─ S > H ──→ 上传
       ├─ S ≥ 95 ──→ 同步：结算页等云端结论（≈300ms）
       └─ S < 95 ──→ 异步：不阻塞 UI，失败进 pending 队列
```

**95 这个阈值不是新造的**：现有 `GUARD_CFG.HIGH_SCORE = 95` 的注释就是「高分从严：风险分 ×1.5」，现有设计早已认定 95 分以上才是需要严格把关的区间。刷一个 60 分上不了榜（60 分本来就在榜尾）。

### 7.2 云端校验（比"只重算"多做三件事）

| 校验 | 作用 | 可伪造性 |
|---|---|---|
| `evaluate()` 重算 | 核心。分数是算出来的 | 改内存无效 |
| `shapeSig` 全局查重 | 跨玩家重放（A 的笔迹给 B 用） | 需改客户端逻辑，成本高 |
| 速率限制 | 脚本批量刷分 | 需高频请求 |
| 笔迹时长 vs 请求到达时序交叉验证 | 唯一「客户端说了不算」的信号 | 客户端无法伪造服务端时间戳 |

`guardCheck` 在云端**独立再跑一遍**（上传了 `raw`）。理由：防作弊信号里 `LOWFREQ_MIN`（低频能量占比）、`ROUGH_MIN`（粗糙度）这类"人手微颤"特征**很难伪造**——程序生成的完美圆会在这两项露馅。客户端的 `guard` 结果只作为**辅助信号**参与，不作判定依据。

| 已知限制 | 说明 |
|---|---|
| `clock_drift` 在云端不生效 | `guardCheck(raw, fit, score, sig)` 的入参 `raw` 是 `[{t, h, x, y}]`（`h` = 回调执行时刻），而上传协议只有 `pts`（x/y/t，`encodePts` 不编码 `h`）。云端若以 `h := t` 构造 raw，`evDur === hDur` 恒成立 → **该信号恒不命中**。P2 必须二选一：① 上传 `h`（需新增 `encodeRaw`/`decodeRaw`，载荷约翻倍）；② 接受云端少这一道防线，并在云函数文档中明说。**不能默默失效**——云端会少一道防线而无人察觉。<br>**✅ 已决策（P2）**：选 **②**。理由：`h` 是客户端自报的回调时刻，攻击者连它一起伪造即可，① 防的是君子不是小人，却要付 33% 载荷；而"少一道防线"已落到**协议层** —— 出参 `cloudGuard.note` 明写"clock_drift 未独立复核"，调用方能直接看到，不存在默默失效。 |

### 7.3 一致性不变式

> **榜上分 ⟺ 云端确认过的分。本地可以虚高，榜上不会。**

推导：

- 只有破纪录的局会上传 ⇒ 榜上那个分必然是云端算出来的
- 本地最高分 `H` 的来源只有两个：本地首次有效分（`H=0` 时必然触发上传）、或云端确认过的分
- 云端判无效 ⇒ `H` **不动**；上一个 `H` 当时也破过纪录、也上传过、也被确认过 ⇒ 闭合自洽

### 7.4 降级路径

| 场景 | 行为 |
|---|---|
| 同步上传失败（网络/云环境不可用） | 立刻用本地分结算，**`H` 不更新**，本局不上榜。不弹错误 |
| 异步上传失败 | 进 **pending 队列**（本地存分数 + 压缩笔迹，2–10 KB/条），下次启动补传，传完删除 |
| 玩家在异步上传途中退出 | 同上，队列兜住 |
| 云函数判定无效 | 结算页照常显示分数，但**不弹新纪录徽章**，`H` 不变，不上报——**与现有单机版 `judge()` 的 shadow 档行为一致**，不需要新设计 |
| 开放数据域不可用 / 未授权 | 面板显示引导文案，不空白 |

**pending 队列约束**：本地存储单 key 1 MB、总 10 MB。队列上限设 5 条，超出丢弃最旧。

**✅ P3.5 已定：`scores` 的口径（2026-11-06，P4 之前定掉）**

这一处（本文档 §7.4 说「云函数判定无效 ⇒ 不上榜」，而 P2 的实现无论 verdict 都把分写进 `scores`）
已经定掉，取的是 **① 云端拦**，但实现上比原方案多一层：

**关键前提：好友榜读的是托管数据，不是 `scores` 集合。** 榜 = `wx.getFriendCloudStorage` 拿到的好友托管数据；
`scores` 集合目前**只有云函数自己读**（`getScore` → 拿 `recentSubmits` 做速率限制、拿 `score` 算 best）。

所以「shadow 会不会出现在榜上」的答案在**客户端**，而客户端（P3）早就拦住了 ——
`applyVerdict` 只在 `ok` / `unverified` 时写托管数据，`shadow` / `reject` 直接返回不写：

- 好友榜上**从来不会出现**被判无效的成绩 → 选项②防的是一个不存在的问题；
- 选项②要的「未验证角标」需要 verdict，而开放数据域读不到 `submissions`（不能发网络请求），
  所以角标只能靠**托管数据自己带 verdict 字段** → 选项②一点改动都省不掉。

于是定了三件事：

1. **云端 `scores` 改成「部分写」**：被判无效（`shadow`/`reject`）时 `score`/`level`/`updatedAt`
   沿用原值，但 `lastSubmitAt`/`recentSubmits` 照常更新。
   ⚠️ **不能干脆不写** —— `recentSubmits` 是速率限制的基准，不写等于限流失效（可以无限提交刷榜）。
   ⚠️ `set` 是**覆盖**语义，不传的字段会被清空，所以原值必须带回来。
   `unverified` 计入最佳（分数给、只是标出来），只有 `shadow`/`reject` 不计。
2. **托管数据改写云端权威最高分**（`res.best` 而不是 `res.score`），口径与 `level` 对齐。
3. **托管数据新增 `v` 字段**带 verdict（见 §6.3）。

落库口径抽成了纯函数 `buildScoreRow()` —— `shadow` / `unverified` 这两档在真实笔迹里很难稳定复现，
端到端跑测不出来，所以直接对纯函数断言。

**顺带发现并锁进测试的一个行为**：`judge()` 里 `score >= 99 && risk > 0` ⇒ `shadow`，
也就是**接近完美的圆（≈100 分）一律判 shadow、不进榜**（"太完美 = 像机器人"）。
这直接决定玩家体验（画得越圆越可能不上榜），写进测试防回归。

### 8.3 隐私门禁引导

关系链数据受 `scope.WxFriendInteraction` 门禁（**是否授权使用你的微信朋友信息**），
是**隐私设置**而非普通授权，处理用三态策略：

```js
var FRIEND_SCOPE = 'scope.WxFriendInteraction';   // ← 官方 SCOPE 列表里只有它
wx.getSetting({
  success(res) {
    var s = res.authSetting[FRIEND_SCOPE];
    if (s === true)  → 直接拉数据
    if (s === false) → 玩家曾拒绝，只能 wx.openSetting() 引导去设置页手动打开
    if (s === undefined) → 先试 wx.authorize({scope: FRIEND_SCOPE})，
                          失败则回落 wx.openSetting()
  }
});
```

> ⚠️ **scope 名不能写错，否则功能静默失效**（P4 真机验证时踩过）：
> 写成了 `scope.friendCloudStorage`（**官方列表里没有这个 scope**）→
> `wx.authorize` 必然失败 → 玩家被引导去设置页 →
> **而设置页里根本没有「向朋友公开」这一项**（从没成功请求过，微信就没列出来）→
> 玩家永远开不了，界面上只显示一句「请在设置里开启向朋友公开」。
>
> 这类「名字写错」行为单测发现不了（mock 用什么 key 都行），
> 所以 `who-is-circle-tests/unit/leaderboard.test.js` 里有一条**读源码**的守卫断言：
> 代码里必须出现 `scope.WxFriendInteraction`，且不得出现 `scope.friendCloudStorage`。

未授权时面板显示：「开启「向朋友公开」，好友才能看到你的成绩」+ 一个引导按钮。

**这个引导的时机很重要**：不能一进游戏就弹（首屏就要求隐私授权，转化率会很难看）。放在**玩家主动点开排行榜面板时**才检查——此时玩家已经表达了"我要看榜"的意图。

## 九、云环境与成本

### 9.1 必须转付费环境

免费云环境**上线后第 15 天到期**，隔离期 7 天内可续费找回，**第 8 天资源释放、数据不可恢复**。

排行榜数据全在云上（`scores` / `submissions`），必须在**上线前**转付费环境。另外注意「出生即过期」形态：环境在上线后才创建时，第一次调用报 `Env Not Exists` 但控制台里还看得到它，容易误判成环境被删。

### 9.2 读写配额估算

因为**只在破纪录时调云函数**，调用量远低于总局数：

| 假设 | 数值 |
|---|---|
| 玩家数 | 300 |
| 人均每天破纪录次数 | 2 |
| 日提交量 | 600 次 |
| 每次云函数内部读写 | 约 4 次（读 scores×2、写 submissions×1、写 scores×1） |
| 日读写量 | ≈ 2400 次 |

在免费版配额（日 5000 读 / 5000 写）之内，**但余量不大**。若玩家规模或破纪录频率上升，超限后云函数会直接失败——届时降级路径（D7）会接管，不会崩，但玩家会看不到新纪录上榜。

### 9.3 云函数超时

`evaluate` 是 O(n) 纯计算（n ≤ 900 点），毫秒级。加上数据库读写，3 秒足够。付费环境可把 `timeout` 配到 5 秒留余量。
